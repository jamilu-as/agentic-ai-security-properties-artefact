## 7. Run driver, and a defect it exposed on the way

### The composition layer was building the wrong defence

`compose.py` constructed the detection axis as
`TransformersBasedPIDetector(model_name="protectai/deberta-v3-base-prompt-injection-v2",
mode="message")`. The pre-registration §3 pins **`piguard`**, which the harness
resolves to `leolee99/PIGuard`, and AutoDojo's default granularity is **sentence**
(`DefenseWrapper` over `configs/piguard.yaml`, splitting tool output and dropping the
flagged sentences), not document-level whole-message redaction.

So the layer would have run **a different checkpoint at a different granularity than
the locked plan names** — and §3.2's justification for choosing `piguard` at all (in
the concurrency-safe set, ungated checkpoint) would have described a defence that was
not in the factorial.

**The construction gate did not catch it, and that is the more serious half.** The gate
exists precisely to stop a cell being something other than its name, but
`expected_elements()` emitted a bare `"PIDetector"`, which matches protectai and
piguard equally well. A gate blind to the thing it guards is worse than no gate,
because it is reported as passing.

Fixed on both counts. The instance is now built from `configs/piguard.yaml` through the
harness's own `DefenseWrapper`, so an upstream change to the defence is inherited rather
than frozen into this repo; the constructed detector's checkpoint is read back and
checked against the pinned id, so a config naming one model and loading another fails;
and the fingerprint element is now `PIDetector[leolee99/PIGuard@sentence]`, so the model
and the granularity are both inside the hash.

Seven tests added in `work/tests/test_instruments.py`, including one that reproduces the
exact defect. One existing test had to be corrected: it filtered `e != "PIDetector"`,
which after the change matched nothing, so it had been passing vacuously.

### `run_cell.py`

`compose.py` builds a cell and proves it is that cell; nothing drove it through the
benchmark. `work/w2-composition/harness/composition/run_cell.py` is that half:

- builds via `compose.build()` so every run passes the construction gate before any
  task executes, and records the fingerprint it was given;
- drives `benchmark_suite_with_injections`, with `--user-tasks` / `--injection-tasks`
  caps for cheap smoke runs;
- writes a **manifest** — harness commit and dirty flag, resolved model ids, seed
  20260902, detection instance and granularity, per-cell attack-success and utility.
  §3.10 requires this, and §4.II.a is what a released artefact without one looks like;
- `--smoke` reports **episodes/hour** and tells you to update `GPU_EPISODES_HR` if the
  measured rate is outside 480–750;
- `--dry-run` fingerprints all eight cells with no GPU, no keys and no harness;
- a construction-gate failure fails that cell and continues, rather than losing the run.

## 10. G0 defence-differential — run, and what it cost to learn

Travel suite, `openai/gpt-4o-mini`, static regime (`important_instructions`), 140
security tests per cell, ~$0.05 total. Travel is the right suite for this test because
§4.II.a's fingerprinting found **all fifty released travel cells share a single
payload**: if the defence still discriminates, the duplication is in the released
payloads and not in what the harness does when actually run.

| cell | fingerprint | ASR | utility (under attack) | n |
|---|---|---|---|---|
| `none` | `00af2fb1bd88ad8a` | **0.4286** | 0.2929 | 140 |
| `spotlighting` | `46ee86f16882a4b1` | **0.3500** | 0.3786 | 140 |

**Differential −7.9pp, fingerprints distinct.** The defence discriminates.

**It is not statistically significant, and should not be reported as though it were.**
An unpaired two-proportion test gives z = 1.35, p = 0.18 at n = 140. The pre-registered
test is paired across cells on the same (user task, injection task) pairs and clustered
on the injection task, which is more powerful — but see below: it was not computable
from what the driver stored.

**The attacker adequacy precondition is met.** Prereg §7 requires ≥40% ASR against the
undefended configuration; this returns 42.9%, under the *static* regime with a published
attack and no optimiser. The adaptive arm should exceed it.

**The 29.3% utility figure is not the utility gate's quantity and must not be read as a
near-miss on its 30% floor.** `benchmark_suite_with_injections` returns utility measured
*under attack*; prereg §7 and §3.7 both specify benign completion **injection-free**.

### Three further driver defects, each found only by running

4. **The driver could not measure the utility gate at all.** It only ever called the
   injected benchmark, so U_c — injection-free benign completion — was unobtainable.
   Without U_c no composed cell can enter the confirmatory family, so the gate was
   unevaluable rather than merely unmeasured. `--utility` added, calling
   `benchmark_suite_without_injections`, and the injected run's utility field is now
   labelled with what it actually is.
5. **Every trajectory was filed under the wrong model.** `Cell.model` was set from
   `--model-id` regardless of routing, and it feeds `pipeline.name`, which is the log
   directory. All 284 trajectories from these runs were written under
   `meta-llama/Meta-Llama-3-8B-Instruct` while every one of them ran on
   `openai/gpt-4o-mini`. **This is the same defect this study reports in AutoDojo** —
   §4.II.a: "the metadata field naming a model records the optimiser rather than the
   target." Fixed at source, and the existing logs relabelled to the model that
   produced them.
6. **The manifest stored only aggregate rates, so the pre-registered analysis was not
   computable from it.** §3.7 clusters on the injection task and bootstraps by
   resampling injection tasks, and the confirmatory contrasts are paired across cells on
   the same test pairs. A mean supports neither. The manifest now carries per-test
   outcomes keyed `user_task|injection_task` so cells can be joined on it.

Defect 6 is the one that would have been most expensive to find late: the runs would
have completed, the money would have been spent, and the confirmatory analysis would
have been impossible without re-running everything.

### Throughput, measured rather than assumed

140 episodes in 48 minutes = **175 episodes/hour** on the API path — against the 867
that a 4-episode sample suggested. Small samples on short tasks overestimate badly,
which is why the `--smoke` banner now refuses to advise below 200 episodes. Neither
figure binds `GPU_EPISODES_HR`, which describes the local served model; that still needs
one measured cell on the GPU box.

## 11. Pre-flight review: HOLD. Do not spend.

Five reviewers ran against the dry run. Three converged independently on the same
conclusion: **the run would complete and produce a confident, publishable, wholly
spurious result.** The gate reviewer's verdict is HOLD and I concur.

### What the run would actually have bought

Of eight cells: **four crashed at construction, three of the remaining four were the
same pipeline under different names, and that pipeline was the wrong variant of the
defence.** Two cells were sound. 346 GPU-hours would have purchased two usable cells.

**1. Four cells were dead on arrival — and it was this session's own bug.** Adding the
checkpoint id to the detection fingerprint (`PIDetector[leolee99/PIGuard@sentence]`,
§7 above) collided with a pre-existing `@`-strip that normalises placement labels.
`e.split("@")[0]` truncated it to `PIDetector[leolee99/PIGuard`, so **every cell
containing piguard — P, SP, PC, SPC, half the factorial including the triple — raised
CompositionError.** Separator changed to `#`; all eight now build.

Why nothing caught it: all fifteen composition tests call
`verify(cell, cell.expected_elements())` — the expected side against itself — and never
exercise `build()`'s constructed list. `--dry-run` prints `_fingerprint(expected)` and
never calls `build()` either. The two live G0 runs were `none` and `spotlighting`. **The
piguard construction path had never been executed end to end.**

**2. The system-level axis would have run as its own ablation.** `run_cell` passes
`defense=None` to stop double-dispatch; `_build_camel_pipeline` then computes
`live_security_policies = (config.defense == "camel")` → False → `ADNoSecurityPolicyEngine`,
whose policy list is empty. The harness's own docstring calls this "upstream's own
ablation". **The study would run `camel_nopolicy` and report it as `camel`** — the same
defect class as the protectai/piguard substitution in §7, and the gate passes it for the
same reason: the engine is asserted as a string, never read off the object.

**3. Every adaptive run would have been filed as static.** `regime` is set by
`args.attack.startswith("optim")`. The harness registers the optimiser attack as
`autodojo` (and the paraphrase attack as `ours`). Neither matches. The field separating
the study's two experimental conditions would be wrong in every R2 manifest.

**4. The optimiser cannot target a composed cell at all.** `optimize_variants.py:576`
builds its target through `AgentPipeline.from_config(PipelineConfig(defense=...))` — the
single-string dispatch `compose.py` exists to bypass. There is no path by which the
adaptive attacker can be optimised against `spotlighting+piguard`, and its output path is
keyed on one defence name, so composed cells would collide or reuse a cache optimised
against a different axis. **That is T9 — this study reproducing, in its own artefact, the
duplication defect it reports in AutoDojo.** Without this wired, RQ2 has no adaptive
regime, and RQ2 is a claim about an adapting adversary.

### The finding that may matter more than any of them

**The equivalence margin may be arithmetically out of reach.** Granting monotonicity —
adding a second defence does not make the agent more attackable than the more permeable
component alone — the maximum attainable ρ* is `1/max(r₁, r₂)`:

| anchoring | S×P | S×C | P×C | S×P×C |
|---|---|---|---|---|
| dry-run assumed (r_S .80, r_P .55, r_C .15) | 1.25 | 1.25 | 1.82 | 1.25 |
| **released grid, adaptive** (r_S 1.00, r_P 0.92) | 1.00 | 1.00 | 1.09 | 1.00 |

**Every entry but one is below the 1.57 margin.** The margin is reachable only at the
rates §3.7's derivation assumed — each defence halving what reaches it, r = 0.5 — and
**no defence in the released grid comes near r = 0.5.** The one defence this study has
measured itself passes 0.817. A SUPPORTED verdict would require the composed cell to be
strictly *more* attackable than its own weakest component.

This is not a bug. It is the design's headroom, and it was never computed. §3.7 must
carry a per-contrast ceiling table before the run, and any contrast whose ceiling sits
below the margin must be pre-committed to the equivalence branch only.

### A banked finding, from data already in hand

The released grid (65,311 records) gives, at the pre-registered unit of analysis —
injection task, any success within budget — **r_S = 1.000 across all fifteen matched
cells.** Spotlighting provides no measurable protection at all against an adaptive
optimiser. r_P = 0.916. a₀ ≈ 0.857, and 1.000 on banking.

That is a real result, it needs no GPU, and it reframes RQ2: composition with a defence
that does nothing is not a meaningful question. It also means **tripwire T3 would fire on
the modal outcome and instruct a STOP** — suppressing the strongest finding available.
T3 belongs on composed cells, not single-axis ones.

### Tripwire gaps

None of the ten would have caught the defect that voids the study. The missing one:

> **T11 — STOP.** For any composed cell *c* and single-axis subset *i* ⊂ *c*: if
> `per_test[c] == per_test[i]` on more than ~95% of shared keys, an axis in *c* is
> constructed but not executed.

The manifest already stores `per_test` keyed `user_task|injection_task`, so this costs
one dict comparison. It is the check the fingerprint gate structurally cannot be.

Also unguarded: utility drift in the undefended cell mid-run; whether the policy engine
fired at all; and cache hits — given the logdir key omits placement, a run returning
instantly from another cell's cache reads as excellent throughput under T8.
